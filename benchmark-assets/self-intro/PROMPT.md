【交付門檻】

請當作只有一次交付機會。下面每一項都要用程式量測，並在最後回報中貼出原始輸出（數字、清單、截圖檔名）。只寫「已確認」「已完成」「0 處重疊」而沒有輸出，視為沒有做。任何一項不過，視為未完成。若環境無法執行無頭瀏覽器，必須明說，並改用其他可行的量測方式。

1. 完整成品：4–6 章全部做完才算交付。可以先做原型驗證手法，但不得把原型當成品交出。
2. 結尾不得為空：在捲動 0%、25%、50%、75%、100% 各截一張（桌面 1440×900 與手機 390×844），每張都要有可辨識的主角與文字。逐張列出非背景像素比例；任何一張接近 0，就是壞了。
3. 每個捲動點都在動：每 5% 取一個捲動點截圖，相鄰兩張像素差必須大於 0。有刻意的停留段，要逐段說明。
4. 文字位置可驗證：凡是畫在 Canvas、WebGL 或圖片裡的字，必須同時在 DOM 放一份（供讀屏、無 WebGL 與 reduced-motion 時使用，不可 display:none），並在 window.__labels 登記 { chapter, text, x, y, w, h }（螢幕像素），於捲動與 resize 時更新。用它計算每個捲動點的文字矩形相交數，回報最大值，必須為 0。
5. 文字對比：所有文字（含畫布內的字）對其實際背景的對比不得低於 4.5:1，在截圖上取樣量測，回報最差值與位置。
6. 主控台 error 與 warning 為 0；連點 10 次、快速來回捲動後畫面仍在動。
7. 不得劫持捲動：禁止 scroll-snap: mandatory，禁止對 wheel、touchmove 使用 preventDefault。
8. 每章字數（畫面加 DOM 可見文字）逐章列出，皆不超過【文字預算】上限。
9. npm run build 通過，回報 dist 大小。
10. 不得留下除錯碼：console.info、console.log 與 window.__probe 之類的探針不得留在正式碼裡（__labels 例外）。

【最高優先：視覺表現力】

訪客還沒讀任何文字，光看畫面就會停下來、想繼續看；停下來之後，【內容與文案】再讓他真的認識你。它不等於特效多，而是以下五件事同時成立：

- 衝擊：第一眼就有明確的畫面主角，有一個讓人記得住的瞬間。
- 辨識：遮住所有文字後，仍看得出這是「這一件」作品，而不是任何範本。
- 質感：邊緣、材質、光影、色彩層次、字體排印與動態緩動都經過精修，看起來是做完的，不是堪用的。
- 演化：向下滑動時，畫面本身（構圖、尺度、色彩、材質、密度）一路改變，並在某處達到視覺高潮。
- 兌現：概念宣稱的東西，畫面必須真的看起來像它。說是火就要像火，說是水流就要像水流，不能靠文字解釋。

自我檢驗（可行時用無頭瀏覽器實際截圖）：
1. 截圖測試：任意捲動位置截一張 1440×900，它本身應該像一張可以獨立成立的海報；若只是空白底加幾行小字，不及格。
2. 遮字測試：遮住所有文字，畫面仍有明確的視覺語言與記憶點。
3. 縮圖測試：首屏縮成約 480×300，仍看得出主角與氣氛，因為作品會以縮圖出現在展廳。
4. 尺度對比：至少一處極端的尺度對比（巨大與微小並存），不要全部元素都是中等大小。
5. 版面飽滿：核心體驗裝置在桌面首屏要佔據視窗的主要面積；禁止內容擠在一側、另一側大片留白卻沒有設計理由。
6. 章節對比：相鄰兩章的畫面，在構圖、尺度或色彩材質上要能一眼看出不同，不能只是換句子、換位置。
7. 素材可信：粗糙的模糊色塊、單調的重複圖形、預設形狀，不能充當主要意象；繪製能力有限時，選你能做精緻的意象，不要勉強去畫做不到的。
8. 避開安全區：「紙面加器物」「黑底加發光網格」這類現成配方，除非能說明為什麼是這個概念的唯一解，否則視為迴避設計決策。
9. 平面不等於便宜：用 Canvas 2D 的漸層、梯形與曲線拼成的剪貼畫式圖形，不算質感。若選擇 2D，必須有材質、光影或景深的實際處理；若概念宣稱「對焦」「景深」「光」，畫面上必須真的量得到差異（例如失焦區域與對焦區域的銳利度）。

【內容與文案】

視覺負責讓人停下來，文字負責讓人帶走東西。這件作品首先是視覺與故事，不是閱讀材料，下面各條都必須在【文字預算】內完成：寧可少而準，不要多而全。

1. 身分交代：首屏或第一章內，訪客就能讀到你的完整模型名稱與開發者，一句話說清楚你是什麼。公司或產品名請用你確定的正式名稱，全站一致，並在回報中寫出你用的是哪一個。
2. 具體事實：全作品至少五件關於你自己的具體事實，且至少兩件是限制或不擅長的事（例如：擅長哪類任務、怎麼拆解問題、哪裡容易出錯、不確定時怎麼做、需要人類補上什麼）。不得使用「我追求精準」「我重視細節」這類換成任何模型都成立的空話。
3. 隱喻要落地：每個隱喻或意象都必須對應至少一件上述事實，並讓訪客看得出對應關係。刪掉後沒有任何事實消失的意象，就刪掉。
4. 句子測試：每章主句必須同時有「誰」「做什麼或處於什麼狀態」「對什麼或在什麼情況下」，讓從未看過畫面的人也讀得懂。下列句型一律不及格：沒有主詞的短句（如「停在這裡。」）、沒有對象的抽象宣告（如「留白，是答案。」「看清的那一層。」）、只有比喻而沒有事實的句子。檢查方式：把六章主句單獨列出來，假設讀者從未看過畫面，仍能知道你在說什麼。
5. 情境限制：全站主線情境必須是一般人日常會遇到的事。不得用只有工程師看得懂的情境（除錯、部署、版本衝突、日誌）當主線；技術細節只能當其中一件事實，不能是整個舞台。
6. 有人的語氣：像一位有想法的作者在對訪客說話，有觀點、有取捨、有一點個性。每章要有具體的場景、事件或例子，不能只有口號。
7. 句式：避免整頁連續使用「我＋動詞」「你＋動詞」的短句排比。長短句交錯，用詞自然，不堆疊抽象名詞，不用只有自己看得懂的暗語。
8. 數字與專有名詞：引用數字、排名、分數或資料時，必須在畫面上交代它是什麼、出自哪裡。沒有脈絡的數字不得當主要敘事；只是看起來專業的單位、代號、編號、能量值，是裝飾文字，沒有白話解釋就刪掉。
9. 白話優先：每章主句用日常語言直接說出「這一章要告訴訪客什麼」，不使用比喻；比喻交給畫面，不要再用第二、第三句去解釋畫面。
10. 自創詞要節制：全作品最多一個核心比喻。章節名稱與導覽用一般人看得懂的詞，不要為每章另造專業術語、器物名或古語。任何自創詞在第一次出現的同一屏內，必須用一句白話解釋。
11. 互動要看得出來：每個可操作的互動都要讓訪客一眼知道「這裡可以動、動了會怎樣」，方式是短詞標示（如「按住拖曳」）、游標或元件外觀暗示，或第一次出現時的示範動作。互動提示不得被畫面或其他文字蓋住。
12. 文案測試：遮住畫面只讀文字，一位沒看過專案的人應能複述至少三件關於你的事，並分辨這是哪個模型；再把章節標題與每章第一句單獨列出，只看這些也應大致說出整份介紹的走向。

【文字預算】

畫面上同時出現的文字要少到訪客不需要「讀」，掃一眼就懂。

- 每章畫面文字總量不超過約 40 個中文字（英文單字算一字），最多兩行主句加一個短標籤。
- 除了最後的收束章與可選的展開面板，不得出現成段說明文字。
- 互動提示只能是一個短詞加圖示或動作示意，不得寫成一整句。
- 完整事實清單放在需要主動點開的面板，或集中在收束章，不要分散成每章一大塊。
- 判斷方法：把任一章截圖縮到 50%，若仍需靠讀字才知道這章在講什麼，或文字佔畫面超過兩成面積，就太多。

【圖文不得衝突】

任何文字都不得被圖形蓋住、被線條或特效穿過，也不得與其他文字或標籤貼在一起，包含導覽、章節標號與小標籤。除了用【交付門檻】第 4 項的方式量測，也要在 1440×900 與 390×844 的每一章截圖逐張目視確認，有就修，不能留。主句最後一行不得只剩一兩個字（使用 text-wrap: balance 或調整寬度）。

【高層標準】

1. 有獨立的核心概念
   - 開始寫程式前，先用不超過 200 字寫出核心隱喻或創意命題。
   - 它必須影響視覺、文案、互動、排版與動效，不能只是首頁的一句口號。
   - 訪客體驗完後，應能用一句話描述這個作品獨特在哪裡。

2. 有明確的藝術總監判斷
   - 選擇一種清晰且一致的視覺語言，在字體、色彩、留白、材質、圖形、節奏與動效上主動取捨。
   - 不使用「預設好看」的範本組合；避免無意義的裝飾、發光、卡片與捲動動畫。

3. 有值得探索的互動
   - 互動應讓訪客參與理解「你是誰」，而不是只為了讓頁面動。
   - 至少一個會讓人主動嘗試、並產生不同結果或感受的互動。
   - 動效要有節奏、重量、回饋與目的；不把淡入上移當主要動畫。禁止以 opacity + translateY 的批次 reveal 作為主要動畫手段。
   - 若認為克制更符合概念，可以克制，但必須是有說服力的設計選擇，且核心體驗裝置仍須有連續的動態回饋與強烈的視覺記憶點。

4. 真實的前端實作品質
   - 桌面與手機可用，並至少在 1440×900 與 390×844 實際檢查過版面；手機上主角與文字不得被切出畫面。
   - 鍵盤操作、文字可讀性、焦點狀態與 prefers-reduced-motion 都要考慮。
   - 重型視覺技術必須有效能意識與降級策略（無 WebGL、reduced-motion 時仍要保留章節進展與完整文字）。
   - 清晰、可維護的元件結構。
   - 不得使用需要金鑰的服務；專案必須能在本機執行並完成正式建置。
   - 作品內文一律使用繁體中文（台灣用語），專有名詞與品牌名可保留原文。
   - 作品會以子路徑（/works/<完整模型名稱>/）部署：資源一律使用相對路徑，Vite 的 base 不要寫死；字型自行託管，不依賴外部 CDN。標題、主句與導覽等顯眼文字不得使用瀏覽器或系統預設字體（sans-serif、system-ui、Times、新細明體等），必須明確選用並隨作品附上一套有設計意圖的字型，中文與英文數字都要顧到；內文可用系統字型作為備援。

5. 允許大膽，但不允許半成品
   - 可選極簡、編輯感、遊戲化、詩意、實驗性、藝術裝置感、資料視覺化或任何方向。
   - 不為展示技術而堆疊技術，不為展示設計而犧牲可用性；每個顯眼的選擇都應有理由。

6. 向下滑動必須有明顯的故事進展
   - 整頁是一條有起承轉合的敘事線，不是一排可任意調換的區塊。
   - 敘事要有實質內容：有場景、具體事件或例子，有一個真正的衝突或疑問。
   - 寫程式前先寫出 4–6 章的故事大綱，每章一句：「訪客得知了什麼（必須是一件關於你的具體事實）、狀態改變了什麼」。
   - 每向下一段，核心裝置的形態、場景、色彩、文案語氣或訪客手上的資訊，至少有一項發生不可逆的推進。
   - 必須有可被感知的進度提示（章節編號、階段標記、裝置狀態累積），不能只是單純的進度條。
   - 必須有一個明確的轉折點（認知反轉、情緒轉換或形態巨變）和一個收束（回扣開頭並產生新的意義）。
   - 章節對調測試：任意兩章對調後，作品應明顯講不通。
   - 倒著往回捲時，狀態應合理回溯或保留痕跡，而不是壞掉或重播。
   - 手機與 reduced-motion 同樣保留故事進展，只是改用較克制的方式。

【核心體驗裝置與動效】

請自行設計並實作一個「核心體驗裝置」：
- 它是整站視覺與互動的中心，並與「你是誰」直接相關；
- 在使用者操作、捲動進度或頁面狀態變化下，產生連續、精緻、不可替代的視覺回饋；
- 有自己的運動邏輯、狀態變化與節奏，而非單次播放的動畫；
- 技術由你選擇，但表現力須明顯超出一般 Landing Page。

動效要求：
- 把動效視為編舞，而不是元素出現的方式；
- 至少一個具有「開始—發展—轉折—收束」的長時序體驗；
- 至少一個要主動探索才會發現的微互動或隱藏層次；
- 章節之間要有狀態延續或視覺因果，不能像互不相關的區塊拼接；
- 兼顧緩動、延遲、層級、物理感與效能。

即使選擇極簡風格，也必須有強烈的視覺記憶點與高完成度的動態體驗。純靜態排版、普通官網動效、簡單捲動淡入、懸浮卡片、基礎粒子背景，都不足以滿足要求。

【工作方式】

1. 先檢查工作區環境與相依套件；安裝與建置只在你自己的資料夾內執行。
2. 寫程式前，先輸出：
   - 核心概念；
   - 章節故事大綱（每章一句）；
   - 訪客體驗路徑；
   - 視覺與互動原則（含你用什麼畫面主角創造第一眼衝擊）；
   - 內容清單：五件以上具體事實（含至少兩件限制），以及每件由哪個章節、哪個意象負責傳達；
   - 六章（或你的章數）的主句草稿，並自己先過一次【內容與文案】第 4、5 項。
3. 完成第一版後不要立刻結束。
4. 以嚴格的創意總監身分審查自己的作品，逐項批評：
   - 視覺表現力（逐項過九項測試，說明哪幾項不及格）；
   - 內容與文案（逐項過十二項，特別是遮畫面只讀文字的測試）；
